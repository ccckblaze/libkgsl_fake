# Measured conclusions: the ioctl surface of `/dev/kgsl-3d0` and the simulation boundary

Environment: one real aarch64 Adreno (a6xx) device with `DEVICE_BITNESS=48`, plus an arm64 container with no
GPU at all, carrying the same closed-source user space (`libOpenCL` / `libgsl` / `libCB` / the 37 MB
`libllvm-qcom`). The image name is deliberately not hard-coded here; see `IMAGE` in `tools/docker_gpless.sh`.

## 1. One complete OpenCL lifetime uses just 12 ioctl numbers
The KGSL ioctl type is `0x09` (not the `0x47` that keeps getting quoted). Bit fields:
`nr = c & 0xff`, `type = (c >> 8) & 0xff`, `size = (c >> 16) & 0x3fff`.

| nr | name | count | phase |
|----|------|-------|-------|
| 0x02 | DEVICE_GETPROPERTY | 10 (one per property, 9 distinct types) | CTX |
| 0x45 | GPUOBJ_ALLOC | 16 | throughout |
| 0x13 | DRAWCTXT_CREATE | 1 | CTX |
| 0x32 | DEVICE_SETPROPERTY | 1 | CTX |
| 0x40 | SYNCSOURCE_CREATE | 1 (+1) | CTX |
| 0x42 | SYNCSOURCE_CREATE_FENCE | 1 | CTX |
| 0x4a | GPU_COMMAND | **1** | launch only |
| 0x49 | GPUOBJ_SYNC | 2 | launch only |
| 0x46 | GPUOBJ_FREE | 16 | teardown |
| 0x14 | DRAWCTXT_DESTROY | 1 | teardown |
| 0x41 / 0x43 | SYNCSOURCE_DESTROY / SIGNAL_FENCE | 1 | teardown |

The device self-description needs only 9 properties (`props/a6xx.properties`). Memory conventions:
- each GPUOBJ is mapped with `mmap(fd, offset = obj_id << 12)`;
- the shadow page sits at `offset = DEVICE_SHADOW.gpuaddr` (`0xfc041000` on this box, size `0x8000`), and the
  timestamps live at `+0x204` inside it (the internal offset given by the third `DEVICE_SHADOW` field);
- **completion is not waited for through an ioctl**: the runtime spins on the mapped page, and `WAITTIMESTAMP`
  style calls appear 0 times over the whole run;
- on a6xx the CPU and GPU share one address space: a `gpuaddr` in the command stream *is* a host pointer
  (`mincore` proves it), so no separate GPU page table has to be maintained;
- the command batch for one launch is `0xa8` bytes = 42 dwords, carried by that single `GPU_COMMAND`.

a6xx uses **type-4 / type-7 packets**, not a5xx's pkt0/pkt3:
- type-7: `(cmd >> 24) == 0x70`, `opcode = (cmd >> 16) & 0x7f`, `size = cmd & 0x3fff`;
- type-4: `(cmd >> 28) == 0x4`, `offset = (cmd >> 8) & 0x7ffff`, `size = cmd & 0x7f`.
`src/rec.c` decodes exactly this. The opcode name table comes from `src/pm4_names.h`, generated by
`tools/genpm4.py` from `adreno_pm4.xml`.

## 2. The compile half: the fake device already emits bit-identical ISA
In a container with **no GPU whatsoever**, the fake device lets the closed-source runtime:
- enumerate `QUALCOMM Adreno(TM)` through `clGetDeviceIDs`;
- succeed at `clCreateContext` / `clBuildProgram`;
- hand back a 2084-byte ISA from `clGetProgramInfo(CL_PROGRAM_BINARIES)` whose sha256
  `4c420fab45914151338e8ec9e0c54a88dfc0d192d9c6cbae36a0959e36f1aad3` is **bit-identical to the real device's**
  (baseline in `tests/golden/`);
- do all of that with 0 unhandled ioctls: the runtime never asked for a requirement we had not recorded.

Three cross-checks on a machine that *does* have the GPU agree with each other:
| run | ISA sha256 |
|-----|-----------|
| `fkgsl --real` (real card) | `4c420fab…` |
| `fkgsl --abort-exec` (fake device hiding the real card) | `4c420fab…` |
| container (no GPU at all) | `4c420fab…` |

The reason: `clBuildProgram` issues **zero `GPU_COMMAND`**, compilation happens in user space inside
`libllvm-qcom`, and the GPU is only used to hand out memory. Repeated runs on the real device produce the same
hash — compilation is deterministic.

## 3. The execute half: not attempted, and why
Doing it would need an a6xx PM4 front end (type-4/type-7 register writes, `CP_LOAD_STATE6`, `CP_EVENT_WRITE`,
HLSQ dispatch, preamble/uniform, the 64-lane float register file semantics) plus an ISA6 interpreter. The public
ecosystem ships disassemblers only (Freedreno, tinygrad `extra/disassemblers/adreno`) and no CPU interpreter for
ISA6; the work is measured in months.

The boundary is hard, and it was measured:
- `tests/tripwire.c` grabs the real device fd with an `svc` instruction and sends a KGSL ioctl straight to it;
  strict mode aborts on the spot (core dump). "Slip past the shim onto a real card" is closed off.
- Once `openat64` was hooked up as well, tinygrad's `QCOMDevice` compute path core dumps on the fake device —
  it reads values the GPU is supposed to have written back, and the fake device cannot supply them.
- `probe full` (submitting a real kernel) spins to timeout on the fake device: advancing the shadow-page
  timestamps covers only the two documented slots, and some runtimes spin elsewhere. `FK_TS_COVERAGE=all` is the
  crude fallback (paint the whole page with the timestamp): it makes the runtime *believe* the work finished, but
  the data read back is necessarily fake, so it exists for hang debugging and never as a usable state.

## 4. Judgment on the upstream toolchain
Upstream `tinygrad_repo/extra/qcom_gpu_driver/opencl_ioctl.py` (284 lines) already patches `libc.ioctl` with an
aarch64 trampoline to decode PM4 plus `LOAD_STATE6`, so the "interception" half is available off the shelf. This
project's recorder is its C-level equivalent; what it adds is that it can wrap non-python targets, such as
`clinfo` or a hand-written C probe.

## 5. Off-device codegen: the code half of a pkl reproduces bit-for-bit, the data half needs a real number source (measured 2026-11-01)
Tool: the model toolchain's own `tools/model_codegen.py`. Bench: a reference machine carrying the same GPU.
Baseline: a model pkl produced on the real device by the upstream codegen example.

### Where to cut, and three traps
Remove nothing but the launch of QCOM kernels on the target device; leave every other step alone. Three traps, all
of them reproduced:

1. The cut cannot go in `ExecItem.run`: that method also performs `ensure_allocated()`, so skipping it means no
   device memory is allocated at all.
2. The cut cannot go **globally** in `CompiledRunner.__call__`: CPU and DISK kernels use this class too, and
   swallowing them breaks the host-side decode chain.
3. The dependency nobody sees: `extra/onnx.py::buffer_parse` `bitcast`s the raw weight bytes (`DISK:<model file>`
   tensors — a plain file read, no GPU involved) into float16, and *that* kernel runs on the target device. Left
   unlaunched it produces 0, `x*0` folds away symbolically, and **the entire vision branch stops generating
   kernels**: the monitoring model drops from 313 scheduled items to 174, same for the captured items;
   `0.7978515625` (fp16 of 2/sqrt(pi)) becomes `0.0` on the fake device, while the same raw bytes `62 3a` read
   correctly out of DISK in both modes. Fix: decode on the host with numpy, then copyin (`np.frombuffer` is
   read-only, so `.copy()` before copyin).

### The compile half: equivalence proven
`--numpy-weights` plus skipping only the QCOM launches, against the real-device-executed reference:

| metric | this run (not committed) | reference (executed on device) | |
|--------|--------------------------|--------------------------------|--|
| items / kernels | 132 / 131 | 132 / 131 | equal |
| src_bytes / lib_bytes | 330761 / 496292 | 330761 / 496292 | equal |
| src_sha | `8b946f26b84bf434` | same | equal |
| lib_sha | `7665068f687ba6fd` | same | equal |
| per-kernel source + ISA | 131 kernels | — | 0 mismatches |

In other words: **without submitting a single GPU command, the output is bit-identical kernel source + ISA +
structure.**

### The data half: a pkl bakes the product of a run, not the model code
`Buffer.__reduce__` copies buffer contents out into the pkl, and `TinyJit(prune=True)` pulls the "depends only on
weights" onetime kernels out of the execution sequence, runs each once in place, and bakes its result into the pkl
as data. Monitoring model: 313 items keep 132, 181 are onetime; with nothing executed, every one of those buffers
is zero. In bytes: the pkl totals 16.8 MB, **the all-zero gap is 16.8 MB** (a set of `imageh` weights at
2.76M/2.46M/1.38M…), and only 87 small buffers agree. Conclusion: most of a pkl's size *is* one real execution's
output.

### CPU replay: working (monitoring model fully green, the rest verified the same way)
Same idea: record the host-side bytes at `Buffer.copyin`, hand each QCOM kernel's AST to the CPU backend to
recompile and rerun, write the result back into the original device buffer, and what gets baked into the pkl at
save time is replayed data. `tools/cpu_image_shim.py` was added to give the CPU renderer OpenCL `image2d`
semantics — the AST is untouched, only the rendering is swapped.

Three semantics that had to be simulated or adapted, all of them measured:
1. **`CLK_ADDRESS_CLAMP`**: convolution windows compute negative coordinates at the image border, and on real
   hardware CLAMP absorbs them (out-of-range reads return 0, out-of-range writes are dropped). The first version
   missed this layer, clang wrote out of bounds, and the process died of a silent segfault.
2. clang's `vector_size` types have no `.x`/`.y` members (those belong to `ext_vector_type`/OpenCL), so components
   are fetched through a pointer.
3. `ClangRenderer` emits coordinates as `(int2){a,b}`, and the preprocessor reads the comma inside the braces as a
   macro-argument separator — so coordinates and written values get an extra pair of parentheses in the pattern.

A trap on the way: the shadow buffers were keyed on `id(Buffer)`; once a buffer was collected its id got recycled
and 28 kernels started reporting "size mismatch". Recording the bytes on the buffer object itself instead cleared
it up.

Measured on the monitoring model (reference machine, 805 CPU replays, all successful):

| check | result |
|-------|--------|
| code half, src_sha / lib_sha | `8b946f26b84bf434` / `7665068f687ba6fd`, same as the real device |
| per-kernel source + ISA | 131 kernels, 0 mismatches |
| material buffers (read, but never written by a captured kernel) | 259 buffers, 258 bit-identical |
| the single difference | 3 floats = a placeholder for one model input, re-copyin'd every run, so the seed value means nothing |
| the 131 activation buffers that do get overwritten | differ from the reference (CPU/GPU rounding plus a different input seed); functionally irrelevant |
| **final check: 4 frames on one fresh input** | real-device pkl / reference GPU pkl / reference CPU pkl agree on all 2384 output floats, bit-for-bit |

Toolchain (this directory, the bench): `tools/offdevice_cpuexec.py` (replay and package),
`tools/check_data_seed.py` (decide which buffers must agree), `tools/run_pkl_pair.py` (replay several frames on one
fresh input and compare outputs), `tools/rollout_models.sh` (roll the check out over every model).

`tools/model_codegen.py` there gained `--cpu-exec` (paired with `tools/cpu_image_shim.py`), one command for a

### What works today
A GPU-less machine produces a complete pkl (code half + data half) with one `cpuexec` command, and
`run_pkl_pair.py` gives output-level acceptance. A machine with a GPU can still use
`model_codegen.py --reference` as the structural regression gate.

## 6. End-to-end packaging in a GPU-less container (measured 2026-11-01)
Host: macOS + Docker Desktop, any linux/arm64 image carrying the `libOpenCL`/`libllvm-qcom` offline compiler and
clang 18. The container has **no `/dev/kgsl-3d0`**.

### The step that stuck: ctypes resolves symbols around `LD_PRELOAD`
`from tinygrad import Device; Device["QCOM"]` took a SIGBUS (rc=135) under the shim, with the stack stopped at
`ctypes.memset` just after `ops_qcom.py:_gpu_alloc`. The root cause is not the mmap logic — it is that **the
interception never applied**: tinygrad's `FileIOInterface.mmap` uses `ctypes.CDLL("libc.so.6").mmap`, meaning it
`dlopen`s a specific library and then `dlsym`s *that handle*, which always returns libc's own implementation and is
therefore invisible to symbol interposition. The fake kgsl fd — a 4 KB memfd — was mapped at 16 MB straight;
`mmap` itself succeeded, and the first touch of an out-of-range page took the SIGBUS. ioctls behaved, because they
go through `fcntl.ioctl` and hit the PLT.

The fix is at the end of `src/interpose.c`: interpose `dlsym` itself, and substitute the shim **only when the
address resolved is exactly libc's implementation**. `RTLD_NEXT` and `RTLD_DEFAULT` lookups are left alone — the
shim resolves the real implementations through `RTLD_NEXT`, and rewriting those would interpose itself into
infinite recursion. Covered: `mmap/mmap64/ioctl/open*/stat*/fstat/access`. `dlvsym` is deliberately not hooked:
taking `mmap` through it still yields libc's version, which then faults loudly on an out-of-range access instead of
quietly sliding onto real hardware.

Measured after the fix, same container: `Device["QCOM"]` initialises, and the staged probe is 5/5 green (allocate /
copyin / direct write into the mapped page / image allocate / image copyin).

### Three models: package in the container, re-verify on a real GPU
Packaging is `tools/docker_gpless.sh` — one command, red-line self-check included. Re-verification is
`tools/run_pkl_pair.py` on the reference machine (several frames on one fresh input, outputs compared) together
with `tools/check_data_seed.py` (buffer classification).

| model | container CPU replays | lib_sha | GPU_COMMAND | output vs device-executed |
|-------|-----------------------|---------|-------------|---------------------------|
| monitoring | 805, 0 failures | `7665068f687ba6fd` | 0 | bit-identical (4 frames, 2384 floats) |
| policy | 171, 0 failures | `01849d9210b56a47` | 0 | bit-identical (3 frames, 3000 floats) |
| vision | 866, 0 failures | `96d34f3a97b7c5a2` | 0 | bit-identical (3 frames, 4728 floats) |

The `lib_sha` matches the artifact from the GPU-equipped build host, which says the code half was not polluted by
the CPU replay; `UNHANDLED` and `TRIPWIRE` are 0 as well. `make test` passes all five stages in the same container.

### A misclassification fixed in the acceptance script
`check_data_seed.py` used to recognise "model input placeholders" from the slots in `captured.input_replace`, but as
soon as a pkl is loaded `__post_init__` calls `_clear_inputs()` and writes `None` into those slots, so none of them
were recognised: the monitoring model's one input placeholder and the policy model's three were counted as
"material, read-only" and reported as mismatches. They are now matched by each input's declared
`(element count, dtype)`, and each input kind may claim a buffer only once (any extra counts as material). A note is
printed when a shape contains a `Variable`. For all three models the "material buffer mismatch" count is 0.

## 7. The thread count a card picked is part of the program (measured 2026-11-02)
Object: the 131 kernels of the monitoring model. Two environments carrying the same closed-source user space — an
aarch64 box with a real card, and a card-less arm64 container where the shim stands in for the device node — plus
the artifact already deployed on real hardware as the baseline. Every timing comes from one script: several frames
on the same inputs, median taken, only the pkl swapped.

### Dimension distribution
| artifact | kernels | `local=1` | no local group at all | fractional global | note |
|----------|---------|-----------|-----------------------|-------------------|------|
| deployed on the real device (table source) | 131 | 35 | 0 | 30 | every kernel carries a card-chosen local group |
| compiled by the card-less box, no table | 131 | 30 | 87 | 0 | timing is always 0, so the pick degenerates to the smallest set or to nothing |

The card-less artifact's 117 = 87 (no local group) + 30 (landing on `local=1`). The fractional `global` values are
what the card's chosen thread count leaves behind in a symbolic division (`global = pre / local`); the card-less
artifact has none at all, which is itself the fingerprint that this graph was never measured by a card.

`tools/pkl_dims.py diff` reconciles against the table harvested from the deployed artifact: the card-made artifact
agrees 131/131 (rc=0), the card-less one agrees 44 and differs on 87 (rc=1). Running the same tool over a
linear-graph artifact from a different model family: 94 kernels, 16 at `local=1`, 31 with a fractional `global`,
agreeing 94/94 with its own table.

### Timing and correctness
| approach | real-card time | output |
|----------|----------------|--------|
| deployed artifact | 12.07 ms | baseline |
| as-shipped path, recompiled on card (1st) | 12.16 ms | bit-identical to baseline |
| as-shipped path, recompiled on card (2nd) | 12.06 ms | bit-identical to baseline |
| card-less box, no table | 277 ms | bit-identical to baseline |
| card-less graph + card table (37 entries changed) | 12.3 ms | bit-identical to baseline |
| greedy rule (exact division only, cap 4→1024) | 22.3 / 25.0 ms | bit-identical to baseline |
| greedy rule (uneven division allowed, round up, cap 64 / 128) | 16.7 / 17.2 ms | **590 of 596 outputs differ** |

Two more observations:
- Two compiles on the same card agree on only **73 of 131** dimension pairs, and on **75** with the deployed
  artifact, yet all three are bit-identical in output — the card's reading is not deterministic, but the values it
  lands on are equivalent to each other.
- The structural half (source plus the full shape before the pick) matches the real device **131/131**, whether a
  card or the shim layer did the compiling.

### Conclusions (correcting last round's recommendation)
1. The thread count is not a "a bit faster, a bit slower" preference. Together with the shape parameters it is part
   of the program contract: **the legal combinations are a strict subset of the candidate space**, and a
   combination the card never stated may simply compute the wrong answer. Last round's "fall back to a rule when
   the table has no entry" is disproven by measurement, and the code has been reverted. Both places the model
   toolchain keeps (`tools/model_codegen.py` and `tools/model_dims.py`) now keep the local value for off-table
   kernels and warn explicitly: correct, not necessarily fast.
2. To get speed, harvest the table from a machine with a card. To find out whether an artifact consulted a table at
   all, use `tools/pkl_dims.py report|diff`.
3. A card's reading is not unique, so **dimension equality cannot be the regression gate** — only output equality
   can. Dimensions are for a distribution health check.

### Designed, not implemented: a fourth loud signal, `GEOM`
The layer currently shouts on three red lines: `GPU_COMMAND` (submitted when it should not execute), `UNHANDLED`
(an ioctl that was never recorded), `TRIPWIRE` (a real device fd leaked). The shared style is to die on the spot
rather than silently hand back something that looks correct.

The error in the last row of the timing table is a different animal — inventing a thread count and computing wrong
is fundamentally **geometry inconsistent with parameters**. The layer can see the ndrange (local/group) in PM4 and
the shape parameters in `kernargs`, yet says nothing when they do not match. The proposal is a fourth signal,
`GEOM`: while decoding `GPU_COMMAND`, reconcile each dispatch's `group_size` against the shapes and strides
recognisable in `kernargs`, and against whatever divisibility the shape implies; on violation, abort loudly
under the same strict rules.

Two rules were drafted for it, and the harvest settles both — one in its favour, one against it.

- **Coverage holds.** Over seven dumps — the deployed artifact (131 kernels), two recompiles on the card, the
  card-less artifact, and the card-swept artifact described below (49 kernels) — every dispatch satisfies
  `shape <= global * local < shape + local`: the groups cover the extent without ever adding a whole extra one.
  131/131 and 49/49, with work groups up to 512 threads represented, so this is a structural invariant rather than
  a legality signal. It is cheap to check and never false-positives, so it goes in.
- **Divisibility does not hold.** The drafted `global % local == 0` check fires on **50 axes of the deployed
  artifact** (29-30 kernels per dump carry a fractional `global` precisely because the card divided an extent the
  local size does not divide: `[4, 5.625, 240]` with `[1, 64, 1]` over `(4, 360, 240)`). A rule that aborts on
  genuine card-made programs is not a red line; it is dropped.

Launch-level refusals do exist, but they never reduce to a number. Wrapping `_time_program` — the one place a
candidate arrives with its `global_size` and `local_size` before the vendor launch — and sweeping the whole
monitoring model on a card gives **10923 timed candidates across 104 searched kernels, 94 of them refused**, every
one `Too many resources requested for launch`. The refusals are not separable by work-group size: **19 of 103
kernels both accepted and refused the same `prod(local)`** (one refusal at 258 threads, while 1024-thread groups
launch fine in the same model). What the card checks is the compiled kernel's own footprint, so the only honest
record is per kernel: which dimensions it took, which it refused, which it timed fastest. The cost of that record is
51 minutes of search for one model (median 9.8 s per kernel, 193.8 s for the slowest), about 68 minutes end to end.

Speed is not derivable either: within a single kernel the slowest accepted candidate is a median 16x the fastest and
up to **2015x**. Only the card's own measurement separates them, which is also why `GEOM` cannot be a formula.

The sweep then caught the cheapest way to measure the wrong program. Run with `NOLOCALS=0 BEAM=2` rather than the
flags the device itself compiles with, the artifact carries card-picked thread counts for only **49 of its 131
kernels**, has **no fractional `global` at all**, and leaves 10 kernels holding groups over 256 threads. That is a
different program family from the deployed artifact, and it will not join to its table even by shape: `model_dims.py`
keys every entry by `sha256(kernel source)[:32]`, so a table harvested under one flag set can never be claimed by an
artifact built under another. The harvest therefore belongs on the box whose flags produced the shipped graph, and
the table travels with those flags.

What is left to build is small and specific: decode the ndrange at `GPU_COMMAND`, apply the coverage invariant, and
look the kernel up in a per-kernel set the card actually accepted — refusing loudly when a dispatch carries a
dimension that set has already seen the card reject. tinygrad's `beam_search` cache table is a starting point, not
the answer: it stores only the winner per kernel, and its rows are keyed by whichever flags were set when the search
ran (the 116 rows on the reference box came out of a `NOLOCALS=1` bench, so 77 of them choose no local group at all).
The candidate sweep above is the shape the real table should have.

## 8. A second generation, on Android/bionic: a cardless bundle that survives save and reload (measured 2026-11-03)

Everything above is a6xx on glibc. This round moved the layer to an **a5xx machine running Android/bionic
(API 23)** and pushed it past `clBuildProgram`, into a flow the earlier sections never touched: a closed
model builder that compiles a whole graph, **saves** it as a bundle of buffers plus compiled programs, and
**reloads** it to check what it wrote. Two questions, answered by measurement.

### Porting to bionic is four rules, and one of them was a live deadlock
1. **The loader cannot be asked from inside a constructor.** bionic's linker lock is not recursive and the
   constructors run while it is held, so `dlsym(RTLD_NEXT, ...)` from a constructor deadlocks. `src/raw.c`
   reaches libc with `svc #0` instead (a table of the eleven entry points this layer needs, with the errno
   translation bionic does in `__set_errno`), the constructors are empty under `__ANDROID__`, and the link
   carries `-Wl,-z,now` because a *lazy* PLT call made during a constructor walks into the same lock.
2. **`ioctl` cannot be defined under its own C name.** bionic declares `int ioctl(int, int, ...)` behind an
   overloadable request macro, so the hook compiles as `fk_ioctl` and the link name is handed out by
   `__asm__(".globl ioctl\n.set ioctl, fk_ioctl")`. `nm -D` shows both names at one address.
3. **No `dlvsym`, so the ctypes side door cannot be bootstrapped** — and is not needed: the native callers
   on this platform resolve `open`/`ioctl`/`mmap` through the PLT, where plain interposition already applies.
4. **Nothing inside a hook may touch stdio.** A library mid-`open` through libc re-enters `fopen`, and
   `fopen` takes bionic's non-recursive `__sinit` lock — debuggerd caught exactly that stack
   (`fopen → __sfp → __sinit → pthread_mutex_lock`) while our `open` hook was still on the frame. All
   logging now goes through one fd-only sink (`fk_sink_*` in `src/log.c`), which glibc uses too, so the
   a6xx baseline stays byte-comparable.

### The interface did not change between generations; the properties and the wait did
Recorded on the a5xx across a full bundle build: `0x02 0x07 0x13 0x14 0x32 0x40 0x41 0x42 0x43 0x45 0x46 0x49
0x4a` — section 1's list with nothing added, and strict mode reports 0 unrecorded. Only the *property* face
differs: 5 reads (`DEVICE_INFO`, `DEVICE_SHADOW`, `UCHE_GMEM_VADDR`, `UCODE_VERSION`, `DEVICE_BITNESS`) against
a6xx's 10, and three of the five carry different values — among them `DEVICE_SHADOW`, whose gpuaddr and size are
what the mmap convention is built on. Hence `props/a5xx.properties`, recorded rather than guessed.

The a5xx runtime then waits on a field of the shadow page that this layer has no name for. With the default
`FK_TS_COVERAGE=shadow` the build stops dead after **12** acknowledged `GPU_COMMAND`s, in
`cl_a5x_wait_for_timestamp_thread`; with `all` the same build reaches **4644** acks and finishes. So on a5xx
`FK_TS_COVERAGE=all` is a requirement of the flow, not the debugging hammer section 4 of the README called it.

### One descriptor per GPU object is one too many
`GPUOBJ_ALLOC` used to answer with a fresh memfd per object, because that is the simplest honest backing.
The kernel driver costs the caller **no** descriptor per allocation — an id and an mmap offset, nothing else —
and on Android/bionic `RLIMIT_NOFILE` is soft 1024 / hard 4096. A whole bundle build peaks at **1005 live
objects** (1120 allocated, 115 freed), so `memfd_create` started failing at exactly that point,
`GPUOBJ_ALLOC` returned `-ENOMEM` **without a log line**, and the closed runtime reported the whole thing as
a single null pointer from `clCreateBuffer` during the reload. Nothing about that symptom names its cause.

`src/mem.c` now keeps **one** memfd and hands out page-aligned slices from it. A slice is never reused, so two
objects can never share a page; the arena span equals everything allocated (203.9 MB over the build, largest
single object 4.0 MB) rather than everything live, and it is sparse until touched. The allocation failure is
logged too, since silent `-ENOMEM` is how this took a whole session to find.

### The bundle: the code half is the card's, the numbers half is the archive's
Same model file, three bundles, compared with `tools/bundle_struct.py`. Objects 1045, binaries 19, kernels 368,
payload area 48,073,644 B in all three.

| bundle | made by | ISA binaries | global dims | local dims | buffer contents |
|--------|---------|--------------|-------------|------------|-----------------|
| shipped | card, last month | — | — | — | baseline |
| card run today | card | **0 of 19 differ** | 0 differ | 68 differ | 190 differ |
| cardless + numbers refilled | this layer + the model archive | **0 of 19 differ** | 0 differ | 86 differ | **0 differ** |

The cardless build's 190 weight-carrying buffers split two ways: **101 arrive correct with no card** (the
runtime serves that copy from the CPU) and **89 come back empty**, because the a5xx runtime performs that
particular upload with a GPU command. The numbers are not lost: they are in the model file, and the layout a
kernel wants is a function of the shape information the bundle already records, so they are recomputed and
written back — which is exactly what the shipped bundle was made of, and why the refilled cardless bundle
matches it byte for byte. Section 5's "the data half needs a real number source" is now stated in its sharpest
form: **the code half is a bit-for-bit copy of the card's output; the numbers must never come from the run.**

Acceptance is the card's own: reload the cardless bundle on the real a5xx and replay it — 368 of 368 kernels
run, rc=0, the same result the shipped bundle gives on the same box.

### Section 7's conclusion repeats on a different artifact family
Local work sizes differ 68/368 between two card runs and 86/368 between cardless and shipped, every product is
at or under the 1024 the device advertises, and pairs where the global extent is not a multiple of the local
group are as common in the card-made bundle (51) as in the cardless one (57) — so uneven division is normal
here, not a cardless fingerprint. Dimension equality remains a distribution health check, never a gate.

## 9. A container is not a board: two identity questions, then a whole model build with no card and no board (measured 2026-11-03)

Section 8 built a bundle on a *device* with the layer in front of its own card. The question a build
without a device asks is harder: can the same happen in a container, where there is neither a card nor a
board?
It can, after two holes are filled -- and neither hole is about the GPU.

### The runtime asks which SoC it is before it asks whether there is a GPU
Driving a real model build inside such a box failed immediately, before a single ioctl reached the layer,
repeated once per model graph:

```
error_code=1006; error_message=Invalid constraint. No GPU device available for target UNKNOWN_SDM;
error_component=Model Validation
```

The target name is read from `/sys/devices/soc0/soc_id` (the runtime also knows the older
`/sys/devices/system/soc/soc0/id`); `strings` over the closed libraries names both. A container's `/sys`
belongs to the host kernel and has no `soc0` at all, so the name comes back `UNKNOWN`, the GPU backend is
refused outright, and **no substitute device layer can be talked into trying** -- it is never consulted.
The recorded identity of the a5xx board is `305` / `MSM8996pro` / `Snapdragon` / `MTP` / `1.1`.

Hence `FK_SYSFS`: a directory standing in for `/sys`, answered through the hooks that already exist
(`open`/`openat`/`open64`/`openat64`, `stat`/`lstat`/`access`, and the raw `syscall()` path for
`open`/`openat`/`stat`/`lstat`/`newfstatat`/`statx`). It mirrors only nodes that were read off a board by
`tools/record_board.sh`; a node the board does not have is absent from the mirror and still unopenable.
With the mirror in place the same build command runs to completion: 368 kernels compiled, saved, reloaded,
exit 0, with no card anywhere in sight.

### The property area has to be a file on the box's own tmpfs
`getprop` answered empty for every key in the box, which is what pointed at the SoC question in the first
place. Android below API 24 keeps the entire property area in one file, `/dev/__properties__`, written by
init at boot; a container begins with no such file, so every property reads back empty and nothing that
asks the platform a question can answer it. Two measurements make this a trap rather than a task:

- **A bind-mounted copy is not enough.** bionic maps that file `PROT_READ | PROT_WRITE, MAP_SHARED` from an
  `O_RDONLY` open -- a mapping tmpfs honors and other filesystems refuse. Mounting the recorded file at
  `/dev/__properties__` leaves `getprop` exactly as empty as having no file at all; copying it into the
  box's own `/dev` (131,072 bytes, mode 0644 after the copy) works. The failure is silent on both sides.
- **It is mapped at process start**, so the fix belongs to the image or its entry point, not to a build
  flag: the box must place it before anything runs.

With the mirror in place the box resolves its target and accepts the GPU backend. The property area is
what the platform is *asked about* rather than what the build *depends on*, and that turned out to matter
for who gets to run the build: measured 2026-11-03 in a box assembled from this layer, the same fixed
source compiles to the same 2024 bytes of ISA with the area copied in and with no area at all, and a whole
model bundle builds cardless and boardless to 1045 objects, 19 compiled programs and 368 kernels either
way (`tools/bundle_struct.py` calls it a soft pass: only the autotuned local work sizes move, which is the
card's own nondeterminism too -- section 7). With the area the box also answers `platform=msm8996` and
`model=OnePlus 3`; without it those read empty. So **a public CI box needs the /sys mirror and not the
property area** -- and that is why the published image carries the mirror and refuses the area, which holds
a serial number and three radio addresses. Anything that does ask the platform still has to hand it over
and have it copied, never mounted.

### What a container build is worth against the card
Same tree, same model files; one artifact made by the device with its card, one made in the box:

| graph (how it is produced) | objects | ISA | buffers | launch dims | file size |
|---|---|---|---|---|---|
| two-step: compile, then write the model file's numbers over the buffer (48 MB) | 1045 = 1045 | 0 of 19 differ | **0 of 1045 differ** | local 70 of 368, global 0 | 48,415,779 vs 48,397,015 |
| one-step: straight from the card's own upload (29 MB) | 741 = 741 | 0 of 20 differ | 131 of 741 differ | local 43 of 282, global 0 | 29,109,106 vs 29,101,476 |

Neither size gap is content. The payload region is the same number of bytes in both (48,073,644 and
28,865,504), and each gap equals the JSON's own shrinkage to the byte (18,764 and 7,630): object ids and
kernel arguments are serialized *pointers*, and the text those pointers take varies with the addresses the
run happened to use. Section 8's warning applies again -- compare structure and payload, never the hash.

The 131 differing buffers of the one-step graph were opened as half precision and counted, because "one ULP" and
"a different number" are not the same finding: 14,364,872 values read, 7,028,091 of them differ, **6,970,894 by exactly
one code**, the largest absolute gap anywhere in the artifact is `0.03125` (one ULP at that magnitude), and
just 323 values are more than 0.01 apart. Every one of them is a rounding difference of the last bit.

Why the two graphs part company is the production flow, not the layer. The two-step graph has *always* been
built as "compile, then write the model file's numbers over the buffer", so cardless against device is two
runs of the same refill, and it comes out exact. The one-step graph is taken straight from the card's own
upload, so the same comparison shows the card's fp16 rounding against a CPU refill's: one ULP, everywhere,
and nowhere more.

### Acceptance is still the card's
Both container-built artifacts were replayed on the a5xx device with no device layer loaded, using the
`--load` path of the compile tool that the same container build produced:

```
clexec: running 368 queued kernels ; replayed <the two-step graph>   RC=0
clexec: running 282 queued kernels ; replayed <the one-step graph>    RC=0
```

### The static binary that made this look broken
With the mirror in place, `cat /sys/devices/soc0/soc_id` in the box still says *No such file or directory*:
`toybox` is statically linked, so `LD_PRELOAD` never gets a turn. Every dynamically linked reader -- the
closed runtime, python -- sees `305`. Check a mirror with a dynamic reader, or the project will
misdiagnose its own working feature.
